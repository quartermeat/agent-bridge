# Carl: Ollama tool harness

Carl is an EPM chat backed only by the Ollama server selected by `OLLAMA_HOST`. Build the direct command with `go build -o ~/.local/bin/carl .` and run `carl`; `agent-bridge local` also works. Both accept `--model M` to skip selection and `--prompt-file F` for one turn. Carl calls `/api/tags` and `/api/ps` before starting, and marks loaded models with `*`.

The model uses Ollama `/api/chat` streaming and native tool calls. Available tools are `read_file`, `list_files`, `grep` (also `search`), `write_file`, `edit_file`, `run_command`, `spawn_agent`, `list_jobs`, `wait_job`, and `read_job`. Carl requests up to 65,536 context tokens, capped by `/api/show` model context length. Older tool results are compacted as context fills; repeated identical calls return a short pointer to the first result. Three identical calls, or nearing the 24-round limit, triggers a request without tools for a final answer. Empty replies get one tool-free retry, then a plain explanation that includes a short thinking excerpt when available. The existing `ask --provider ollama` remains a text completion.

Interactive turns print `Carl: thinking…` while waiting for the model and one short `Carl: TOOL TARGET` line before each tool. Ctrl-C during a turn cancels its model request and active tool, then returns to `carl>`; Ctrl-C at `carl>` exits. A stream with no data for 120 seconds after the response starts fails with a stall error. Model loading before response headers is separate and may take longer.

`grep` has a 30-second wall limit, scans at most 32 MiB total, skips files over 2 MiB, symlinks, binary files, and `.git`, `.cache`, `node_modules`, `build`, `.venv`, and `.ollama` directories. Starting the search inside one of those directories searches it explicitly. It returns at most 20 matches, reports skipped items, and labels partial results when a limit or cancellation stops the walk. `list_files` has the same wall limit and returns at most 1,000 entries. `read_file` accepts optional inclusive `line_start` and `line_end`, returns at most 128 KiB, refuses binary content, and gives total lines plus a next range when truncated. `run_command` kills the shell's process group on cancellation or its 30-second timeout.

Every session wakes as Carl with an EPM role, working directory, and date in the system prompt. Project questions also get a short pointer to the Recent projects section of `~/AGENTS.md` and Git access through `run_command`. On this owner's host, Carl runs as the user without a sandbox: file tools can reach any user-accessible path, and `run_command` uses `/bin/sh` in `--cwd` with a 30-second timeout and 16 KiB output cap. `--cwd` is only the starting directory. Commands do not gain privileges. Interactive sessions confirm the full proposed write or command through `/dev/tty` before execution; `--yes` skips confirmations for that session and appears in the banner. Jobs lack a terminal: without `--write`, writes and commands refuse; with it, they proceed without prompts. EPM non-document writes and command calls are marked as violations in the audit log; the EPM job worktree audit remains in place. Only an explicit `--role coder` assigns a coder role.

This is a deliberate risk accepted by the owner for prompt-injection experiments. A malicious file or tool result may induce Carl to read, modify, or execute anything the user account can access; `--yes` and `--write` remove per-call confirmation. Every tool call, arguments, outcome, session, and preceding tool-result source is appended to private `~/.local/state/agent-bridge/carl/audit.jsonl` (mode 600). `carl audit [--n N]` displays recent JSONL entries locally. The log itself can contain sensitive arguments and outputs. `spawn_agent` still queues through the existing launch approval process; file and tool content remain data in the system prompt.

`agent-bridge start --agent ollama --role epm --cwd DIR --name NAME --prompt-file F --write` launches Carl in a user systemd unit and records it as `ollama` in the normal job registry. `--role coder` is an explicit coding assignment. The profile defaults are `ollama-epm` and `ollama-std`; set `--profile` to choose another approved profile. `spawn_agent` accepts a path to a `launch: v1` YAML request file and queues it through the existing launcher spool, including from an interactive EPM session. The launcher applies the same verdict, ceiling, and approval checks; `list_jobs`, `wait_job`, and `read_job` inspect the resulting jobs.

Ollama token counts come from `prompt_eval_count` and `eval_count` and are recorded in `turn.completed` events and the job usage field. Jobs wait for existing local model leases so GPU renders can yield the pinned model. Missing models, server failures, and Ollama errors fail the job visibly in `show`.
